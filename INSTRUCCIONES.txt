==============================================================
 ⚠  PUNTO CRÍTICO — RÉPLICAS EN KUBERNETES / DOCKER SWARM
==============================================================

 El servicio "app" SIEMPRE debe correr con UNA SOLA instancia.
 NO se puede escalar a 2 o más réplicas.

 ¿Por qué?
   WhatsApp solo permite que un número esté conectado desde
   un lugar a la vez. Si corren 2 pods con la misma sesión,
   WhatsApp desconecta ambos y las sesiones se caen.

   Es el mismo comportamiento de WhatsApp Web: si abres la
   sesión en otro navegador, el anterior se desconecta.

 En Kubernetes (04-app.yaml):
   replicas: 1   ← NUNCA cambiar este valor

 En Docker Swarm:
   deploy:
     replicas: 1  ← NUNCA cambiar este valor

 Los demás servicios (postgres, redis) sí pueden tener
 configuraciones de alta disponibilidad sin problema.

==============================================================
 VARIABLES DE ENTORNO — Dónde y cómo configurarlas
==============================================================

 Las variables de entorno son los valores secretos del sistema
 (contraseñas, claves). Dependiendo de la plataforma se
 configuran de forma diferente:

 ── DOCKER COMPOSE (VPS / EC2 / servidor propio) ─────────────

   Se crea un archivo llamado ".env" en la misma carpeta
   donde está el docker-compose.yml.

   Formato del archivo .env:
   ┌─────────────────────────────────────────┐
   │ POSTGRES_PASS=mi-password-seguro        │
   │ JWT_SECRET=una-clave-larga-y-aleatoria  │
   └─────────────────────────────────────────┘

   Docker Compose lo lee automáticamente al hacer:
     docker compose up -d

   Tip para generar un JWT_SECRET seguro:
     openssl rand -hex 32

 ── KUBERNETES ────────────────────────────────────────────────

   No existe archivo .env. Las variables van en el archivo
   kubernetes/01-secrets.yaml como valores en base64.

   Para convertir un valor a base64:
     echo -n "mi-password-seguro" | base64

   Luego se pega el resultado en el secrets.yaml y se aplica:
     kubectl apply -f kubernetes/01-secrets.yaml

 ── RESUMEN ───────────────────────────────────────────────────

   Docker Compose → archivo .env en el servidor
   Kubernetes     → 01-secrets.yaml en el cluster
   En ambos casos → NUNCA subir estos valores al repositorio

==============================================================
 PARA EL CLIENTE — Despliegue en producción (servidor)
==============================================================

 REQUISITOS:
   - Servidor Linux (Ubuntu 22.04 recomendado)
   - Docker instalado: https://docs.docker.com/engine/install/
   - Mínimo 2 GB de RAM

--------------------------------------------------------------
 PASO 1 — Crear la carpeta del proyecto en el servidor
--------------------------------------------------------------

  mkdir ~/notificaciones && cd ~/notificaciones

--------------------------------------------------------------
 PASO 2 — Copiar el docker-compose.yml al servidor
--------------------------------------------------------------

  Desde tu máquina local ejecuta:

    scp docker-compose.yml usuario@IP-SERVIDOR:~/notificaciones/

  El archivo docker-compose.yml se copia exactamente como está.
  NO es necesario modificarlo — las imágenes ya están en Docker Hub
  y todos los valores internos (puertos, rutas, servicios) ya
  están configurados correctamente.

--------------------------------------------------------------
 PASO 3 — Crear el archivo .env en el servidor
--------------------------------------------------------------

  cd ~/notificaciones
  nano .env

  Escribe ÚNICAMENTE estas dos líneas:

  ┌─────────────────────────────────────────────────────────┐
  │ POSTGRES_PASS=una-password-segura                       │
  │ JWT_SECRET=una-clave-larga-y-aleatoria                  │
  └─────────────────────────────────────────────────────────┘

  Guarda con: Ctrl + X → Y → Enter

  ⚠  IMPORTANTE — ¿Por qué solo 2 variables?

  En desarrollo local el archivo .env tiene muchas variables
  (REDIS_URL, DATABASE_URL, PORT, NODE_ENV, etc.) porque Node.js
  corre directamente en la máquina y necesita saber dónde
  conectarse a cada servicio.

  En producción con Docker, el docker-compose.yml ya define
  todas esas variables internamente (NODE_ENV=production,
  REDIS_URL=redis://redis:6379, etc.). Solo delega al .env
  los dos valores secretos que cambian por instalación:
  la contraseña de la base de datos y la clave JWT.

  Tip para generar un JWT_SECRET seguro:
    openssl rand -hex 32

--------------------------------------------------------------
 PASO 4 — Levantar el sistema
--------------------------------------------------------------

  docker compose up -d

  La primera vez descarga las imágenes desde Docker Hub,
  puede tardar unos minutos dependiendo del internet.

  Verificar que todo esté corriendo:

    docker compose ps

  Todos los servicios deben aparecer en estado "healthy" o "Up".

  ⚠  SI EL PUERTO 80 YA ESTÁ EN USO:

  Algunos servidores ya tienen otro servicio usando el puerto 80
  (por ejemplo n8n, Apache, otro nginx, etc.). En ese caso el
  contenedor opsguard-nginx fallará al iniciar.

  Solución — editar docker-compose.yml y cambiar el puerto:

    ports:
      - "8080:80"    ← cambia 80 por cualquier puerto libre

  Puertos recomendados: 8080, 8081, 8888
  Luego accedes por: http://IP-DEL-SERVIDOR:8080

  Para verificar qué puertos están ocupados en el servidor:
    sudo ss -tlnp | grep LISTEN

--------------------------------------------------------------
 PASO 5 — Abrir el panel en el navegador
--------------------------------------------------------------

  Si usas puerto 80 (sin conflicto):
    http://IP-DE-TU-SERVIDOR

  Si cambiaste el puerto (ej: 8080):
    http://IP-DE-TU-SERVIDOR:8080

  Usuario:    admin
  Contraseña: admin123

--------------------------------------------------------------
 PASO 6 — Cambiar la contraseña (IMPORTANTE)
--------------------------------------------------------------

  Dentro del panel → clic en tu nombre arriba a la derecha
  → "Cambiar contraseña"

 SSL — Activar HTTPS en el servidor
==============================================================

 El sistema soporta dos modos de instalación:

 ┌─────────────────────────────────────────────────────────┐
 │  SIN SSL → solo necesitas 2 archivos en el servidor     │
 │  CON SSL → necesitas 4 archivos + carpeta ssl           │
 └─────────────────────────────────────────────────────────┘

 ── MODO SIN SSL (HTTP en puerto 8080) ───────────────────────

   Estructura en el servidor:

     ~/notificaciones/
         ├── docker-compose.yml
         └── .env

   Acceso: http://IP-DEL-SERVIDOR:8080

   Pasos:
     mkdir ~/notificaciones && cd ~/notificaciones
     scp docker-compose.yml usuario@IP:~/notificaciones/
     nano .env   ← agrega POSTGRES_PASS y JWT_SECRET
     docker compose up -d

 ── MODO CON SSL (HTTPS en puerto 8443) ──────────────────────

   Estructura en el servidor:

     ~/notificaciones/
         ├── docker-compose.yml
         ├── .env
         ├── nginx.conf          ← sobrescribe config de la imagen
         └── ssl/
             ├── cert.pem        ← tu certificado (fullchain.crt)
             └── key.pem         ← tu llave privada

   Acceso: https://tu-dominio.com:8443

   ¿Por qué server_name _; en nginx.conf?
   El guión bajo es un comodín que acepta CUALQUIER dominio.
   No necesitas editar el archivo por cliente — funciona con
   cualquier dominio que apunte al servidor.

   Pasos:
     mkdir ~/notificaciones && cd ~/notificaciones

     # 1. Copiar archivos desde tu máquina
     scp docker-compose.yml nginx.conf usuario@IP:~/notificaciones/

     # 2. Crear .env
     nano .env   ← agrega POSTGRES_PASS y JWT_SECRET

     # 3. Crear carpeta ssl y copiar certificados
     mkdir ssl
     cp /ruta/fullchain.crt  ~/notificaciones/ssl/cert.pem
     cp /ruta/dominio.key    ~/notificaciones/ssl/key.pem

     # 4. Levantar
     docker compose up -d

   ⚠  Los certificados NO van al repositorio.
   La carpeta nginx/ssl/ está en .gitignore.
   Nunca subas cert.pem ni key.pem al repo.

 ── SI EL PUERTO 8443 YA ESTÁ OCUPADO ────────────────────────

   Cambia 8443 por cualquier puerto libre (ej: 9443, 8444).
   El certificado SSL funciona en cualquier puerto.

==============================================================
 CÓMO FUNCIONA EL ENVÍO EN PARALELO (referencia técnica)
==============================================================

 El sistema usa BullMQ como cola de mensajes. La concurrencia
 del worker se ajusta automáticamente al número de sesiones
 WhatsApp que estén listas (conectadas y autenticadas).

 EJEMPLO CON 2 SESIONES (Anahi y Vero):

   t=0s    Anahi  → envía job 1 ┐
           Vero   → envía job 2 ┘  (al mismo tiempo)

   t=3-6s  Anahi  → espera delay ┐
           Vero   → espera delay ┘  (cada una su propio delay)

   t=6-12s Anahi  → envía job 3 ┐
           Vero   → envía job 4 ┘  (al mismo tiempo de nuevo)

   Dos carriles paralelos independientes. Cada sesión tiene su
   propio ritmo de 3–6 s entre envíos, no se esperan entre sí.

 REGLA: sesiones = carriles paralelos
   1 sesión  → 1 mensaje a la vez, secuencial
   2 sesiones → 2 mensajes al mismo tiempo
   5 sesiones → 5 mensajes al mismo tiempo

 SOBRE EL RATE LIMIT DE WHATSAPP:
   WhatsApp puede bloquear temporalmente un número si detecta
   que envía mensajes muy rápido (ráfaga). El delay de 3–6 s
   entre cada envío existe precisamente para evitar esto.
   Si ocurre un rate limit, el sistema reintenta automáticamente
   hasta 5 veces con backoff exponencial (15s → 30s → 60s...).
   Los jobs finalmente se completan sin intervención manual.

 POOLS Y ORDEN:
   Si se necesita que los mensajes lleguen en orden estricto
   a un grupo, configurar un pool con UNA sola sesión para ese
   grupo. Con 1 sesión los jobs se procesan en secuencia exacta.
   Con múltiples sesiones el orden puede variar levemente.
