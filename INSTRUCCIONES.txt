==============================================================
 OPCIÓN A — Instalación SIN SSL (HTTP)
==============================================================

 Estructura de archivos en el servidor:

   ~/notificaciones/
       ├── docker-compose.yml   ← recibes este archivo
       └── .env                 ← lo creas tú en el servidor

 Acceso: http://IP-DEL-SERVIDOR:8080

 PASO 1 — Crear carpeta y copiar el compose:

   mkdir ~/notificaciones
   # Desde tu máquina local:
   scp docker-compose.yml usuario@IP-SERVIDOR:~/notificaciones/

 PASO 2 — Crear el archivo .env en el servidor:

   cd ~/notificaciones
   nano .env

   Escribe ÚNICAMENTE esto:
   ┌─────────────────────────────────────────────────────────┐
   │ POSTGRES_PASS=una-password-segura                       │
   │ JWT_SECRET=una-clave-larga-y-aleatoria                  │
   └─────────────────────────────────────────────────────────┘

   Guarda con: Ctrl + X → Y → Enter

   Tip para generar JWT_SECRET seguro:
     openssl rand -hex 32

 PASO 3 — Levantar el sistema:

   docker compose up -d

   La primera vez descarga las imágenes de Docker Hub.
   Puede tardar unos minutos según el internet.

 PASO 4 — Verificar que todo corre:

   docker compose ps
   # Todos deben aparecer como "healthy" o "Up"

 PASO 5 — Acceder al panel:

   http://IP-DEL-SERVIDOR:8080
   Usuario:    admin
   Contraseña: la de ADMIN_PASS en tu .env o, si no la pusiste,
               la generada que aparece UNA vez en:
               docker compose logs app | grep Bootstrap

 PASO 6 — Cambiar contraseña (IMPORTANTE):

   Panel → clic en tu nombre arriba → "Cambiar contraseña"


==============================================================
 OPCIÓN B — Instalación CON SSL (HTTPS)
==============================================================

 Estructura de archivos en el servidor:

   ~/notificaciones/
       ├── docker-compose.yml   ← recibes este archivo
       ├── .env                 ← lo creas tú en el servidor
       ├── nginx.conf           ← recibes este archivo
       └── ssl/
           ├── cert.pem         ← tu certificado SSL
           └── key.pem          ← tu llave privada SSL

 Acceso: https://tu-dominio.com:8443

 PASO 1 — Crear carpeta y copiar archivos:

   mkdir ~/notificaciones
   # Desde tu máquina local:
   scp docker-compose.yml nginx.conf usuario@IP-SERVIDOR:~/notificaciones/

 PASO 2 — Crear el archivo .env en el servidor:

   cd ~/notificaciones
   nano .env

   Escribe ÚNICAMENTE esto:
   ┌─────────────────────────────────────────────────────────┐
   │ POSTGRES_PASS=una-password-segura                       │
   │ JWT_SECRET=una-clave-larga-y-aleatoria                  │
   └─────────────────────────────────────────────────────────┘

 PASO 3 — Copiar certificados SSL:

   mkdir ssl
   cp /ruta/a/tu/fullchain.crt  ~/notificaciones/ssl/cert.pem
   cp /ruta/a/tu/dominio.key    ~/notificaciones/ssl/key.pem

   ⚠  Los certificados NUNCA van al repositorio Git.
      Solo existen en el servidor.

 PASO 4 — Levantar el sistema:

   docker compose up -d

 PASO 5 — Acceder al panel:

   https://tu-dominio.com:8443
   Usuario:    admin
   Contraseña: la de ADMIN_PASS en tu .env o, si no la pusiste,
               la generada que aparece UNA vez en:
               docker compose logs app | grep Bootstrap

 PASO 6 — Cambiar contraseña (IMPORTANTE):

   Panel → clic en tu nombre arriba → "Cambiar contraseña"

 NOTAS SOBRE SSL:
   - El nginx.conf usa server_name _; (acepta cualquier dominio)
     No necesitas editarlo por cliente.
   - Si el puerto 8443 ya está ocupado, cámbialo por 9443 u otro.
   - Para verificar puertos ocupados: sudo ss -tlnp | grep LISTEN


==============================================================
 PROBLEMA: Puerto 80 o 443 ya está en uso
==============================================================

 Si el servidor tiene otro servicio (n8n, Apache, etc.) usando
 el puerto 80 o 443, el contenedor nginx fallará al iniciar.

 Solución — editar docker-compose.yml en el servidor:

   # SIN SSL — cambia el puerto:
   ports:
     - "8080:80"    ← puedes usar 8080, 8081, 8888

   # CON SSL — cambia el puerto:
   ports:
     - "8080:80"
     - "8443:443"   ← puedes usar 8443, 9443, 8444

 Luego: docker compose up -d --no-deps nginx

 FLUJO DE TRABAJO — GitLab CI/CD
==============================================================

 El archivo .gitlab-ci.yml automatiza todo:

 ── PUSH a cualquier rama ─────────────────────────────────────
   → Corre los 35 tests automáticamente en servidores de GitLab
   → Si falla algún test → notificación por email
   → Tú no haces nada, GitLab lo corre solo

 ── GIT TAG (ej: v1.0.4) ──────────────────────────────────────
   → Construye las 3 imágenes Docker en paralelo
   → Sube a Docker Hub con tag vX.X.X y latest
   → Build multi-arch (amd64 + arm64) automático

 DÍA A DÍA:
 -------------------------------------------------------

   # 1. Trabajas en develop normalmente
   git add .
   git commit -m "descripción del cambio"
   git push origin develop        ← tests corren automático

   # 2. Cuando está listo para producción
   #    → En GitLab: merge develop → main
   #    → Luego crear el tag:
   git tag v1.0.4
   git push origin v1.0.4         ← build automático en GitLab

   Ver el pipeline: GitLab → Build → Pipelines

 VARIABLES EN GITLAB (configurar solo una vez):

==============================================================
 VARIABLES DE ENTORNO — Local vs Producción
==============================================================

 ¿Por qué en producción solo hay 2 variables y local tiene más?

 LOCAL (.env con muchas variables):
   Node.js corre directo en la máquina y necesita saber dónde
   conectarse a cada servicio (Redis, PostgreSQL, etc.)

 PRODUCCIÓN (.env con solo 2 variables):
   Docker Compose ya define todas las variables internamente.
   Solo delega al .env los valores secretos que cambian
   por instalación: contraseña de BD y clave JWT.

 Variables que maneja docker-compose.yml automáticamente:
   NODE_ENV, REDIS_URL, DATABASE_URL, POSTGRES_HOST,
   POSTGRES_DB, POSTGRES_USER, JWT_EXPIRES

 Variables que debes poner en .env del servidor:
   POSTGRES_PASS  → contraseña de la base de datos
   JWT_SECRET     → clave de cifrado para tokens JWT

==============================================================
 ⚠  CRÍTICO — RÉPLICAS (NUNCA escalar la app)
==============================================================

 El servicio "app" SIEMPRE debe correr con UNA SOLA instancia.

 ¿Por qué?
   WhatsApp solo permite una conexión activa por número.
   Si corren 2 instancias con la misma sesión, WhatsApp
   desconecta ambas. Es igual que abrir WhatsApp Web en
   dos navegadores — el primero se desconecta.

 En Kubernetes (04-app.yaml):
   replicas: 1   ← NUNCA cambiar

 En Docker Swarm:
   deploy:
     replicas: 1  ← NUNCA cambiar

 Los demás servicios (postgres, redis) sí pueden escalar.


==============================================================
 CÓMO FUNCIONA EL ENVÍO EN PARALELO
==============================================================

 BullMQ maneja la cola. La concurrencia = número de sesiones
 WhatsApp conectadas.

 EJEMPLO CON 2 SESIONES (Anahi y Vero):

   t=0s    Anahi  → envía job 1 ┐
           Vero   → envía job 2 ┘  (al mismo tiempo)

   t=3-6s  Anahi  → espera delay ┐
           Vero   → espera delay ┘  (cada una su ritmo)

   t=6-12s Anahi  → envía job 3 ┐
           Vero   → envía job 4 ┘  (al mismo tiempo)

 REGLA: 1 sesión = 1 carril paralelo
   1 sesión  → 1 mensaje a la vez
   2 sesiones → 2 mensajes simultáneos
   5 sesiones → 5 mensajes simultáneos

 RATE LIMIT:
   El delay de 3–6 s entre envíos evita bloqueos de WhatsApp.
   Si ocurre rate limit → reintenta automáticamente hasta 5
   veces con backoff exponencial (15s → 30s → 60s...).

 ORDEN ESTRICTO:
   Si necesitas que los mensajes lleguen en orden exacto,
   usa UNA sola sesión para ese grupo.
